Module 4.1

What Makes a Technical PRD Different?

A standard marketing PRD says: "Allow users to instant-book homes." A Technical PRD specifies the distributed concurrency lock, the database transaction isolation level (to prevent double bookings), API response schemas, latency SLAs, and edge-case fallbacks.

🎯

1. Problem & Business Metrics

Why are we building this now? What is the measurable metric of success (e.g. increase booking conversion by 14%, reduce API latency under 250ms)?

⚙️

2. System Contracts & Data Schemas

Direct references to API endpoints, JSON payload parameters, database entity mutations, and third-party service dependencies.

🛡️

3. Edge Cases & Degraded States

What happens if the SMS provider lags? What happens if two guests click "Book" in the exact same millisecond? What if payment times out?

Module 4.2

Functional Requirements (FR) vs. Non-Functional Requirements (NFR)

Functional Requirements (FR)

"What the system must explicitly do."

  • FR-1: The system shall allow guests to filter listings by "Instant Bookable".
  • FR-2: The system shall automatically charge the saved payment method upon booking confirmation.
  • FR-3: The system shall dispatch a confirmation email and SMS to both host and guest within 10 seconds.

Non-Functional Requirements (NFR)

"How well the system must perform."

  • Latency: The Instant Book API endpoint must return a response in < 400ms at the P95 percentile.
  • Concurrency / Idempotency: The calendar reservation engine must use Redis distributed locks (Redlock) to guarantee zero double bookings.
  • Availability: 99.99% uptime SLA for checkout services.
  • Security: All credit card data must be tokenized via PCI-DSS Level 1 compliant vault.
Module 4.3

Acceptance Criteria: The Gherkin Standard (Given-When-Then)

Engineers and QA teams write automated integration tests directly against your acceptance criteria. Vague statements like "it should work quickly" cause bugs; explicit Gherkin specifications eliminate ambiguity.

Gherkin Syntax Example: Airbnb Instant Book
Scenario: Guest successfully completes an Instant Book on an available calendar date
  Given a verified guest is logged in with a valid payment method on file
  And listing #44021 has Instant Book enabled by host
  And the dates 2026-12-01 to 2026-12-05 are marked as "Available"
  When the guest clicks the "Instant Book Now" button
  Then a distributed lock is acquired on listing #44021 for 60 seconds
  And a payment authorization for $450 is submitted to Stripe
  And the booking status transitions to "CONFIRMED"
  And the dates are immediately marked as "RESERVED" in the calendar service
  And an HTTP 201 response is returned to the client in < 500ms.
Module 4.4: Real-World Public Product Case Studies

Case Studies: Airbnb "Instant Book" & WhatsApp E2EE

Airbnb, Inc.

How Airbnb Solved the Double-Booking Race Condition

Historically, Airbnb required guests to send a message and wait up to 24 hours for a host to accept. "Instant Book" transformed conversion, but introduced extreme technical concurrency challenges.

The Technical Problem

Distributed Race Conditions

What happens if Guest A and Guest B both click "Instant Book" for the same Parisian loft in the exact same second? If the database isn't isolated properly, both get charged and arrive at the same door!

The TPM Solution

Distributed Lock + Optimistic Locking

Airbnb's TPM specified a temporary distributed lock on the listing date range using Redis. Guest A gets the lock; Guest B's transaction immediately fails with a clean UI notification: "Someone is currently reserving these dates."

Data Consistency

Host Rule Matrix Evaluation

Before confirming, the backend evaluates 12 host rules in < 50ms: Minimum star rating (>4.5), government ID verified, no negative reviews, and minimum stay notice.

Edge Case Handling

Host Calendar Sync (iCal)

If the host also lists on Booking.com, Airbnb continuously ingests background iCal feeds to block external bookings before an Instant Book is confirmed.

WhatsApp / Meta

Technical Specs for 2 Billion Encrypted Users

WhatsApp's End-to-End Encryption (Signal Protocol) ensures that not even WhatsApp servers or governments can read private chats.

Cryptographic Architecture

Double Ratchet Algorithm

Every single message generates a brand new ephemeral encryption key. Even if a hacker compromises today's key, they cannot decrypt past or future messages (Forward Secrecy).

Store and Forward

Zero Message Storage on Servers

WhatsApp servers only act as transient relays. Once a message is delivered to the recipient's phone, it is permanently deleted from WhatsApp servers!

Offline Queuing

Handling Disconnected Clients

If the recipient's phone is off, the encrypted blob stays in an Erlang server queue for up to 30 days, waiting for a push notification wakeup.

TPM Lesson

Security vs User Experience

The TPM designed security number verification: if a contact gets a new phone, WhatsApp displays a subtle chat notification rather than blocking the conversation entirely.
