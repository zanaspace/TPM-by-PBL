Module 8.1

Vertical Scaling (Scale Up) vs. Horizontal Scaling (Scale Out)

When an app gets slow under traffic, you have two architectural choices. A Technical PM understands the financial and technical boundaries of both:

Vertical Scaling (Scale Up)

Buying a bigger single computer (e.g. upgrading an AWS EC2 instance from 8GB RAM to 128GB RAM).

  • Pros: Zero code changes; no distributed system complexity.
  • Cons: Hard physical ceiling; exponentially expensive; single point of failure (if that box dies, everything dies).

Horizontal Scaling (Scale Out)

Adding more commodity servers behind a Load Balancer (e.g. running 10 micro-instances instead of 1 monster).

  • Pros: Virtually infinite scale; high resilience (if 1 server dies, 9 keep serving).
  • Cons: Servers must be strictly stateless (sessions stored in Redis, not server memory).
Module 8.2

Multi-Tier Caching: The Secret to Sub-50ms Latency

⚡

1. In-Memory Cache (Redis)

RAM is 100,000x faster than disk. Storing hot objects (user profiles, active sessions, product prices) in Redis avoids expensive database queries.

🌐

2. Content Delivery Networks (CDN)

Placing images, CSS, JavaScript, and static JSON at edge servers in London, Tokyo, and Lagos means data travels 5ms instead of crossing oceans.

💣

3. Cache Invalidation Pitfalls

"There are only two hard things in Computer Science: cache invalidation and naming things." — Phil Karlton. Setting proper Time-To-Live (TTL) is a core TPM responsibility.

Module 8.3

Database Scaling Techniques: Read Replicas & Sharding

Read Replicas (Primary-Replica Pattern)

In most products, reads outnumber writes 10:1 or 100:1. We configure 1 Primary DB (handles all INSERT, UPDATE, DELETE) that continuously streams changes to 3 Read Replicas (handles all SELECT queries). This quadruples read throughput instantly!

Database Sharding (Horizontal Partitioning)

When a single table reaches 100 million rows, queries slow down even with indexes. Sharding splits the table across multiple physical databases using a Shard Key (e.g. Users with ID 1–1M on DB-1, Users 1M–2M on DB-2).

Module 8.4: Real-World Public Product Case Studies

Case Studies: Shopify & Twitter / X

Shopify Inc.

Handling 76+ Million Requests Per Minute with Zero Downtime

During BFCM (Black Friday Cyber Monday), Shopify merchants generate billions of dollars in hours. A 10-second crash means millions in lost sales.

Pod Architecture

Isolated Tenant Pods

Shopify partitions merchants into "Pods". If Gymshark runs a mega flash sale with 10M visitors, their pod auto-scales without impacting other stores!

Database Connection Pooling

PgBouncer Tuning

Prevented thousands of worker threads from exhausting MySQL connections by sharing a pool of pre-warmed idle database handles.

Twitter / X

The Celebrity Fan-Out Problem

When Elon Musk or Taylor Swift posts a tweet, writing that tweet to 100 million follower timelines simultaneously would melt Redis memory.

Hybrid Fan-Out Architecture

Fan-Out on Write vs Read

For ordinary users with < 25,000 followers, tweets are pushed directly into follower home timelines. For mega accounts, tweets are merged at read time when the user opens the app.
