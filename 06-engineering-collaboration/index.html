Part 1

How code travels from a laptop to customers

Git is a tool that keeps every version of the code, so many engineers can work at the same time without overwriting each other.

Think of a shared recipe book in a restaurant. Nobody scribbles straight into the main book. You copy a recipe, try your changes, and ask the head chef to check before it goes into the book.

🌿

Branch = your own copy

The main branch is the code customers use. An engineer makes a branch (e.g. feature/save-card) to work safely without breaking main.

💾

Commit = a save point

Like a checkpoint in a video game. Each commit saves a small change with a note, e.g. "Add save-card checkbox". You can always go back.

🙋🏽

Pull request = "please check my work"

A pull request (PR) asks the team to review the changes before they are merged (joined) into main. GitLab calls it a merge request.

Part 2

Talking with engineers so they trust you

Engineers work best with TPMs who are clear, curious and respectful of their time. You don't need to write code — but how you ask matters a lot.

🎯
Bring the problem, not the solution

Say what users need and why. Let engineers suggest how — they often find a simpler way.

🚫
Avoid the word "just"

"Can you just add a button?" makes hard work sound easy. Ask "How big is this?" instead.

🎧
Protect focus time

Coding needs long, quiet blocks. Group your questions, and don't ping someone for every small thing.

📝
Write it down

Decisions made in a hallway get forgotten. Put them in the ticket or PRD so everyone sees the same thing.

❓
Ask, don't guess

"I don't understand — can you explain it like I'm new?" builds trust. Pretending to understand breaks it.

⚖️
Talk in trade-offs

"If we do X this sprint, what do we give up?" is better than "Can we have everything by Friday?"

    Part 5

    Real examples: GitHub and GitLab

    The two most popular homes for code. Both shape how millions of engineers work together.

    The story: GitHub (owned by Microsoft) is where most of the world's open-source code lives, with over 100 million developers. Pull requests, as most teams use them today, were made popular by GitHub.

    🛡️ Rules on main

    • Teams can protect main: no merging unless, for example, 2 people approved and all checks are green.
    • The rules work even when people are in a hurry.

    🤖 GitHub Actions

    • Robots run on every change: tests, style checks, security scans.
    • They can also build a preview link, so non-engineers (like you!) can try the change.

    🐜 Small and often

    • Many teams merge small PRs into main several times a day, instead of keeping big branches for weeks.
    • Unfinished features stay hidden behind feature flags (Week 5).

    ⏱️ Size matters

    • A 50-line PR can be reviewed properly in minutes.
    • A 2,000-line PR often waits days — and reviewers miss more problems.
    🎓 TPM lesson from GitHub: when you break work into small tickets (Part 3), you also get small PRs — which are reviewed faster and ship with fewer bugs.

    The story: GitLab is a similar tool — and a company with no offices. Thousands of staff work remotely across many countries, so they had to get very good at working in writing.

    📖 A public handbook

    • GitLab's company handbook is public, with thousands of pages on how they work.
    • Anyone can suggest a change to it — with a merge request, just like code.

    ✍️ Write first, meet second

    • Big ideas start as a written proposal people comment on, in their own time zone.
    • Meetings are for what writing couldn't settle.

    🗂️ Remember the "why"

    • Teams record important decisions (often called decision records): what was decided, and why.
    • A year later, new people understand why things are the way they are.

    🌍 Async by default

    • Nobody should need to be online at the same moment to make progress.
    • Clear tickets, PRs and docs replace "quick calls".
    🎓 TPM lesson from GitLab: clear writing is a superpower. A good ticket, PRD or PR comment saves hours of meetings — especially in remote teams.

    Saturday class

    Questions we will discuss together

    Think about your answer first, then tap to see one good answer.

    1. Should a TPM ever comment on a pull request? Isn't that the engineers' job?

    A good answer: Yes — but on the right things. Engineers judge the code. The TPM checks the outcome: does it match the acceptance criteria, are error screens there, are analytics events included, does it work in the preview? Leave naming, style and design patterns to engineers.

    2. An engineer says: "This change is huge, but it's fine — just approve it." What do you do?

    A good answer: Politely push back. Big PRs are hard to review, so problems slip through. Ask if it can be split into smaller PRs (for example by screen, or by backend and frontend). If it truly can't, ask for an extra reviewer and more testing time.

    3. The automatic checks are red, but the engineer says "the test is flaky, ignore it". Should you approve?

    A good answer: Not yet. Ask them to re-run it or fix the flaky test first. If the team learns to ignore red checks, one day a real problem will be ignored too. A green check is a team promise.

    4. Two engineers disagree on how to build something. How can a TPM help?

    A good answer: Don't pick a side on the technology. Bring them back to the facts the TPM owns: what users need, the deadline, the risk, the cost. Ask each for the trade-offs, write them down, and if needed let the tech lead decide. Then record the decision and the reason.
