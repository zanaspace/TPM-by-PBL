Module 6.1

Git Fundamentals Every Technical PM Must Know

Git is a distributed version control system. You don't need to write terminal git rebase commands daily, but you must understand how code travels from a developer's laptop to production.

🌿

Branches (`main` vs `feature/`)

Developers never commit directly to production (`main`). They cut an isolated branch (e.g. feature/stripe-webhooks), write code, and merge only after approvals.

📦

Commits & Pull Requests (PRs)

A commit is a snapshot of changed files. A Pull Request is a formal proposal asking team members: "Please review my code before I merge it into the main codebase."

🤖

CI/CD Automation Pipelines

Every PR triggers automated robots: running unit tests, linting code style, scanning for security vulnerabilities, and creating temporary staging preview links.

Module 6.2

The TPM Pull Request Review Checklist

Engineers review the code syntax and algorithmic complexity; as a TPM, you review the PR for functional completeness, risk, and user impact:

✅ What the TPM Checks on a PR

  • Acceptance Criteria Match: Does this PR deliver the exact behavior promised in the PRD?
  • Database Schema Migrations: Does the migration add a non-nullable column without a default value? (This could lock large production tables!)
  • Analytics & Telemetry Events: Are the tracking events (e.g. track('checkout_completed')) included in this PR?
  • Staging Preview Test: Open the ephemeral preview URL on mobile and test edge cases.

🚫 What the TPM Leaves to Engineers

  • Variable naming conventions and whitespace formatting (handled by automated linters).
  • Internal design patterns (Factory vs Singleton classes).
  • Memory pointer allocations and garbage collection optimizations.
Module 6.3

Decomposing Product Requirements into Engineering Tasks

A product requirement like "Add 2-Factor Authentication via SMS" cannot be given to a developer as a single giant ticket. A TPM breaks it down across the stack:

Sub-Task ID Layer / Component Technical Task Description Est. Points
ENG-201 Database Add phone_number, is_2fa_enabled, and two_factor_secret columns to users table with migration. 2 pts
ENG-202 Backend Service Integrate Twilio Verify API SDK; implement POST /auth/2fa/send-otp endpoint with rate limiting (max 3 SMS/hour). 3 pts
ENG-203 Backend Service Implement POST /auth/2fa/verify-otp endpoint with 60-second OTP expiration logic and audit logging. 3 pts
ENG-204 Frontend (Client) Build 6-digit OTP input UI modal with countdown timer and "Resend SMS" button. 3 pts
ENG-205 QA & Edge Cases Automated end-to-end integration tests: invalid OTP, expired OTP, and Twilio API outage fallback. 2 pts
Module 6.4: Real-World Public Product Case Studies

Case Studies: GitHub & GitLab

GitHub / Microsoft

How 100M+ Developers Collaborate Seamlessly

GitHub builds tools that define how the entire global software industry develops and ships code.

Branch Protection

Enforcing Quality Gates

GitHub allows TPMs and EMs to enforce branch rules: require 2 senior engineer approvals, require all CI unit tests to pass, and require a linear commit history before merge.

GitHub Actions

Automated Workflows

On every commit, GitHub Actions spins up isolated Docker containers to run tests, calculate code coverage, and deploy to staging.

Trunk-Based Flow

Merging to Main Several Times a Day

GitHub engineers avoid long-lived branches. Features are broken into tiny PRs (< 200 lines of code) and merged into main continuously.

TPM Lesson

Small PRs Ship Faster

A PR with 50 lines gets reviewed in 10 minutes. A PR with 1,000 lines sits for 5 days and causes bugs. As a TPM, encourage engineers to split massive PRs!

GitLab, Inc.

Asynchronous RFCs & Public Handbook Culture

GitLab pioneered all-remote product collaboration using public merge requests for company-wide decisions.

RFCs in Git

Decisions Documented as Code

Instead of endless Slack debates or lost Google Docs, major architectural changes are proposed as Markdown files in a Git repo where stakeholders comment on specific lines.

ADRs

Architectural Decision Records

GitLab preserves the historical "Why": why a database was chosen, why an API was deprecated. New hires understand system context instantly.
