Module 2.1

What is Systems Thinking for a Product Manager?

Systems thinking means viewing your product not as isolated UI buttons or standalone features, but as an interconnected ecosystem of services, data flows, queues, and feedback loops where changing one part can cause ripple effects across the entire system.

🔄

Feedback Loops & Cascading Effects

If the user checkout flow adds a synchronous fraud check that takes 800ms, does that cause database thread pools to exhaust during flash sales? A TPM anticipates downstream bottlenecks before writing the first line of code.

🧱

Coupling & Cohesion

High Cohesion: Components that belong together live together. Loose Coupling: If the email notification service crashes, users must still be able to log in, browse, and place orders without interruption.

⚖️

The CAP Theorem Trade-off

In distributed systems, you can only pick two of three: Consistency (every read receives latest write), Availability (every request receives a non-error response), and Partition Tolerance (system works despite network drops).

Module 2.2

Architecture Patterns: Monolith vs. Microservices vs. Event-Driven

Every engineering team engages in debates over architecture. As a TPM, your job is to evaluate the business and operational trade-offs.

Architecture Style How It Works When to Choose (TPM Pros) Hidden Traps & Costs (TPM Cons)
Monolithic Architecture All application code (Auth, Billing, Catalog, Search) lives in a single codebase and deploys as a single unit. Fast initial iteration, simple local debugging, zero network serialization overhead, unified database. Single point of failure; one developer's bug can bring down the entire app; scaling requires scaling everything.
Microservices Architecture System is split into distinct, independently deployable services communicating over HTTP/gRPC. Autonomous engineering squads, independent horizontal scaling, tech stack flexibility per service. Distributed tracing complexity, network latency, data consistency challenges, DevOps overhead.
Event-Driven (Async Pub/Sub) Services produce and consume messages via event brokers (Apache Kafka, RabbitMQ, AWS SQS) without waiting. Extreme resilience to traffic bursts, loose coupling, non-blocking asynchronous user experiences. Eventual consistency, message deduplication needed, complex debugging of message replay.
Module 2.3

Data Modeling: Entity Relationship Diagrams (ERDs) for TPMs

An ERD is the visual blueprint of how your product's data is stored and connected. If you can define the entities, attributes, and relationships, you can clearly communicate feature requirements to backend engineers.

🔑 Core ERD Building Blocks

  • Entity: A real-world noun stored in the database (e.g. User, Order, Product).
  • Attribute: A property of an entity (e.g. email, price_cents, created_at).
  • Primary Key (PK): A unique identifier for every row (e.g. user_id (UUID)).
  • Foreign Key (FK): A reference in one table that points to the PK of another table to establish relationships.

🔗 Relationship Cardinality Types

  • 1-to-1 (1:1): A User has one UserProfile; a UserProfile belongs to one User.
  • 1-to-Many (1:N): An Author has many Articles; each Article belongs to one Author.
  • Many-to-Many (N:M): A Student enrolls in many Courses; a Course contains many Students (Requires a Join Table like Enrollments).
Module 2.4: Real-World Public Product Case Studies

Case Studies: Netflix & Instagram

Netflix, Inc.

How Netflix Re-architected for 1000+ Microservices

In 2008, a corrupted database shut down Netflix DVD rentals for 3 days. That catastrophic event sparked Netflix's 7-year cloud migration to AWS and microservices.

Architecture

Zuul Gateway & Chaos Monkey

  • Zuul Edge Gateway: Directs 100% of global Netflix streaming requests, handling auth, routing, and canary deployments.
  • Chaos Engineering: Netflix intentionally kills random microservices in production (Chaos Monkey) to test resilience.
Media Ingestion

Video Encoding Pipeline

  • When a filmmaker uploads a 4K ProRes master file, Netflix splits it into thousands of 5-second chunks.
  • Encodes chunks in parallel across 120 different bitrate/device profiles (Mobile, 4K OLED, Safari, Android).
Content Delivery

Open Connect CDN Appliances

  • Netflix embeds custom hardware CDN boxes (Open Connect Appliances) directly inside local Internet Service Providers (ISPs).
  • 95% of video data never leaves your city's local ISP network.
TPM Takeaway

Availability Over Consistency

  • If the personalized recommendation service fails, Netflix does not show an error screen.
  • It gracefully falls back to a cached static list of "Trending Movies". The user never knows a service crashed!
Instagram / Meta

Instagram's Social Graph & Read-Heavy Architecture

Instagram has an extreme 100:1 read-to-write ratio. For every photo uploaded, it is viewed thousands or millions of times.

ERD Design

The Core Entities

  • Users Table: user_id (PK), username, password_hash, is_verified.
  • Posts Table: post_id (PK), user_id (FK), caption, created_at.
  • Media Table: media_id (PK), post_id (FK), s3_url, dimensions.
  • Follows Table: follower_id (FK), followee_id (FK).
Scale Strategy

Fan-Out On Write vs Fan-Out On Read

  • Regular Users: When a user posts, it fans out and injects the post ID into each follower's feed cache in Redis.
  • Celebrities (Cristiano Ronaldo): Fan-out on write would overwhelm Redis (600M followers!). Instead, celebrity posts are merged at read time.
Database Sharding

PostgreSQL Sharding Strategy

  • Instagram partitioned their PostgreSQL database across thousands of shards using custom 64-bit ID generation.
  • IDs embed timestamp, shard ID, and auto-increment sequence in a single integer!
TPM Takeaway

Design for Asymmetry

  • A TPM must evaluate the read/write profile before picking a database. Read-heavy products require aggressive caching and database read replicas.
