Part 1

What is an API?

An API (Application Programming Interface) is an agreed way for two pieces of software to talk.

Buttons and screens are how people use an app. An API is how computers use it.

📖

The menu = API documentation

A restaurant menu tells you what you can order and how to ask for it. API documentation does the same for engineers: "here is everything you can ask our system to do."

🧾

The order slip = a request

The waiter writes your order on a slip with a fixed format the kitchen understands. A request is that slip, sent from one computer to another.

🍛

The food = the response

The kitchen sends back your food — or a message like "sorry, we're out of fish". A response is the answer, with a short status code saying how it went.

Part 2

Actions and answers: methods and status codes

Every request says what action it wants (the method). Every response starts with a 3-digit number saying how it went (the status code). You only need a few of each.

🛠️ The 4 main actions

Think of your phone's contact list:

GET
Read / look at somethingOpen a contact. Nothing changes.
POST
Create something newAdd a new contact. Place a new order.
PATCH
Change part of somethingEdit just the phone number.
DELETE
Remove somethingDelete the contact.

You may also see PUT: it replaces the whole thing at once, instead of one part.

🚦 Status codes are like traffic lights

2xx
It worked200 OK • 201 Created • 204 Deleted, nothing to show
4xx
The app (the one asking) made a mistake400 something wrong or missing • 401 who are you? • 403 not allowed • 404 not found • 429 too many requests
5xx
The server had a problem500 crash / bug • 503 too busy or down

Easy trick: 4xx = "for you to fix". 5xx = "the server's fault".

        Part 5
        
    Real examples: Stripe and Google Maps
    
      
    
      
    Both companies sell their API as the product. Engineers love Stripe's; businesses pay Google for every Maps request.
    

      
    
        
        
      
    

      
    
        
    The story: Stripe lets any business accept card payments with just a few lines of code. It grew into one of the world's most valuable private tech companies, largely because engineers found its API so clear and predictable. (Stripe also owns Paystack in Nigeria.)
    
        
    
          
    
            
    🧭 Easy-to-guess addresses
    
            
      
              
    • POST /v1/payment_intents starts a payment.
      • 
              
    • GET /v1/payment_intents/pi_123 checks it.
      • 
              
    • Every ID has a prefix (pi_, cus_) so you know what it is just by looking.
      • 
            
    
          
    
          
    
            
    🛡️ No double charges
    
            
      
              
    • Apps send an Idempotency-Key with each payment.
      • 
              
    • If the same key comes twice, Stripe gives back the first answer instead of charging again — exactly what you saw in the simulation.
      • 
            
    
          
    
          
    
            
    🔔 Webhooks with a signature
    
            
      
              
    • Some payments finish later (e.g. bank approval). Stripe calls your server when it's done.
      • 
              
    • Each webhook is "signed", so a scammer can't send a fake "payment successful" message.
      • 
            
    
          
    
          
    
            
    💬 Errors you can act on
    
            
      
              
    • Not just "error", but card_declined + insufficient_funds.
      • 
              
    • So the app can say exactly the right thing: "Not enough money — try another card."
      • 
            
    
          
    
        
    
        
    
          🎓 TPM lesson from Stripe: a good API is a product. Clear names, safe retries and helpful errors make other teams faster — and make your users' experience better.
        
    
      
    

      
    
        
    The story: Uber, Bolt and Jumia all use Google's map APIs for addresses, routes and arrival times. Google charges for every request, so a careless design can cost a company a lot of money.
    
        
    
          
    
            
    🔎 Asking with the address
    
            
      
              
    • GET …/directions/json?origin=Yaba&destination=Ikeja
      • 
              
    • It's a GET because it only reads information. The details go in the address after the ?.
      • 
            
    
          
    
          
    
            
    🚦 Limits per key
    
            
      
              
    • Each company has a limit on requests per second.
      • 
              
    • Go over it and Google answers 429 / OVER_QUERY_LIMIT — the map stops working until you slow down.
      • 
            
    
          
    
          
    
            
    📦 Squeezing the answer
    
            
      
              
    • A route has thousands of GPS points. Instead of a huge list, Google packs them into one short coded string.
      • 
              
    • Smaller answers = faster apps and less mobile data for users.
      • 
            
    
          
    
          
    
            
    💰 Every letter can cost money
    
            
      
              
    • The search box suggests addresses as you type. If the app asks Google on every letter, costs explode.
      • 
              
    • Smart apps wait until you pause typing. Try it below 👇
      • 
            
    
          
    
        
    

        
    
          
    ⌨️ Try it: type a delivery address

          🎓 TPM lesson from Google Maps: when an outside API charges per request, how often your app calls it is a product and budget decision — not just a technical one.

        Saturday class
        
    Questions we will discuss together
    
      
    
      
    Think about your answer first, then tap to see one good answer.
    
      
    
        
    
          1. Why should the secret payment API key never be inside the phone app?
          
    
            
    A good answer: Anyone can download an app and dig through it. If the secret key is inside, a scammer could copy it and make payments or refunds as if they were ChopNow. Secret keys stay on the backend. The phone only talks to ChopNow's own backend.
    
          
    
        
    
        
    
          2. A customer was charged twice after their network dropped. What would you ask the engineers?
          
    
            
    A good answer: "Do we send an idempotency key with every payment, and do we reuse the same key when we retry?" Also: "Does the app stop the user tapping Pay twice, and does it show a clear 'still processing' message instead of a frozen screen?"
    
          
    
        
    
        
    
          3. Webhooks are better than polling — so why do good teams still poll sometimes?
          
    
            
    A good answer: Webhooks can get lost (your server was down for a minute, or the network failed). A slow backup check — for example, asking about any payment still "pending" after 10 minutes — catches the ones that slipped through. Webhook first, polling as a safety net.
    
          
    
        
    
        
    
          4. The payment company returns "401 Unauthorized". Whose fault is it, and what should the customer see?
          
    
            
    A good answer: It's ChopNow's fault — our key is wrong or expired. The customer should never see "401". Show a friendly message and a Plan B ("Card payments are down for a moment — pay on delivery?"), and alert the engineers automatically.
