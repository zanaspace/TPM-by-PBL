Module 5.1

The 4 Core Agile Ceremonies & The TPM's Role

1. Backlog Grooming / Refinement

Frequency: Weekly (45–60 mins)

TPM Role: Walk through upcoming user stories and technical enablers. Clarify requirements, ensure acceptance criteria are complete, and confirm the team reaches the Definition of Ready (DoR).

2. Sprint Planning

Frequency: Bi-weekly on Mondays (60 mins)

TPM Role: Define the Sprint Goal. Present prioritized items based on team velocity (e.g. 40 points). Defend trade-offs when an engineer says "We cannot fit feature B without dropping feature C."

3. Daily Standup (Scrum)

Frequency: Daily (15 mins strict)

TPM Role: Listen for blockers! If a developer is stuck on third-party API documentation or waiting on another team's database migration, the TPM unblocks them immediately.

4. Sprint Retrospective

Frequency: End of every sprint (45 mins)

TPM Role: What went well? What slowed us down? Action items to improve pipeline automation, testing, or requirement clarity next sprint.

Module 5.2

The 70 / 20 / 10 Capacity Allocation Framework

Non-technical PMs often make the fatal mistake of allocating 100% of engineering bandwidth to new visible features. Over time, code turns into spaghetti, systems crash, and velocity drops to zero. As a TPM, you protect engineering health.

🚀

70% Product Features

User-facing capabilities, growth initiatives, conversion funnels, and revenue-generating features agreed upon in the product roadmap.

🔧

20% Technical Debt & Infra

Database indexing, refactoring legacy classes, upgrading vulnerable NPM/Python packages, improving CI/CD build speeds, and reducing latency.

🔬

10% Spikes & Exploration

Timeboxed research investigations (e.g. benchmarking PostgreSQL vs ClickHouse for an upcoming analytics feature) before committing full sprint points.

Module 5.3

Story Points & Fibonacci Estimation: Why Hours Don't Work

Why Story Points Over Hours?

A senior engineer might build a feature in 3 hours that takes an intern 3 days. Estimating in hours creates friction. Story points measure relative complexity, effort, and risk, regardless of who writes the code.

  • 1 Point: Trivial text change or config tweak.
  • 2–3 Points: Standard API endpoint with existing pattern.
  • 5 Points: Complex feature touching frontend, backend, and DB.
  • 8 Points: High complexity, multiple external integrations, substantial risk.
  • 13+ Points: Too big! Must be broken down into smaller sub-stories.

Definition of Ready (DoR) vs Done (DoD)

DoR (Before work starts): PRD approved, designs attached, acceptance criteria written, dependencies unblocked.

DoD (Before release): Code reviewed by 2 engineers, unit test coverage > 80%, passed staging QA, deployed to production behind feature flag.

Module 5.4: Real-World Public Product Case Studies

Case Studies: Linear & Slack

Linear.app

Why Top Silicon Valley Startups Left Jira for Linear

Linear revolutionized engineering workflows by rejecting heavyweight enterprise bureaucracy in favor of keyboard-first, high-velocity sprints.

Cycles vs Sprints

Continuous Flow Over Artificial Deadlines

Linear replaces stressful 2-week sprints with repeating "Cycles". Unfinished work automatically rolls into the next cycle without shame or arbitrary rescheduling rituals.

Git Automation

Automated PR Status Transitions

When an engineer branches git checkout -b john/lin-102-auth-token and opens a GitHub PR, Linear automatically transitions the issue to "In Review". Zero manual dragging required!

Triage Inbox

Customer Bug Quarantine

Customer feedback doesn't pollute the active sprint backlog. It lands in a dedicated "Triage" queue where the TPM approves, merges, or archives before engineers ever see it.

TPM Lesson

Speed as a Feature

Linear's sync engine uses local SQLite in the browser. Interacting with tickets takes 0ms latency. Fast tools create fast teams.

Slack / Salesforce

Deploying Code 100 Times a Day with Feature Flags

Slack cannot afford to bring down enterprise workplace communications during a release. Here is how their engineering squads ship safely.

Feature Flagging

Decoupling Deploy from Release

Code is merged into production daily, but hidden behind dynamic feature flags (LaunchDarkly). The TPM turns on the feature for 1% of users, tests metrics, and gradually ramps to 100%.

Canary Testing

Dogfooding on Slack Employees

Every new build runs internally across 3,000 Slack employees for 24 hours before a single external customer receives the code.

Rollback Automation

Instant 60-Second Revert

If Sentry detects an error spike above 0.1%, automated canary watchdogs flip the feature flag to OFF automatically without engineering intervention.

TPM Lesson

Blameless Post-Mortems

When outages happen, the focus is never on blaming the developer who pushed the commit, but on fixing the missing automated guardrail.
